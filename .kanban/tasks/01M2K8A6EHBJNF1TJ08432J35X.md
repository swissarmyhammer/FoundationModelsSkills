    ### True cause found

    I did add print traces for a time. I did read the traces. I did remove the traces after use.

    The cause was not a failed `open(2)` from too many open files. I did prove this: `ulimit -n` on this host is 1048576. Too many open files is not possible here.

    The true cause: `MarketplaceCache`'s lock file handles did not set `O_CLOEXEC`. A marketplace skill can run a script or a shell command (the `shellInjection` and `scripts` grants, marketplace.md §6.7). Each such run forks a child process. A forked child inherits every open file handle of the parent process, unless the parent set `O_CLOEXEC` on that handle.

    `flock(2)` is tied to the open file, not to the process. When a `RunScriptTests` or `ShellInjectionTests` test forked a child process at the same moment a marketplace snapshot lease was open, the child kept a live copy of that lease's file handle. The store then closed its own handle and thought it released the lease. The lock stayed, because the forked child still held its own copy. A probe in a different, concurrent test then found the "released" snapshot folder still locked.

    I found this with `lsof` on a failed run. It named the true holder: a `bash` process and a `sleep` process (from `RunScriptTests`' `sleep-and-background.sh` fixture), not the marketplace store.

    ### The fix

    The fix is in the source, and also in one part of the test.

    Source fix — `Sources/FoundationModelsSkills/Marketplace/MarketplaceCache.swift`: I added `O_CLOEXEC` to the three `open(2)` calls that make a lock file handle — the snapshot lease, the exclusive check that cleanup runs, and the writer lock. A forked child no longer inherits any of these handles, so a `close(2)` in this process now truly ends the lock everywhere.

    Test fix — `Tests/FoundationModelsSkillsTests/MarketplaceTestSupport.swift`: `SnapshotLockProbe.isLocked` opens its own probe handle the same way, with the same risk. I added `O_CLOEXEC` there too, for the same reason.

    Neither fix adds a sleep, a retry, or a hard-coded time value. Neither fix serializes the test or skips it.

    ### Proof of the fix

    30 full `swift test` runs in a row, after the fix, all green: `theStoreHoldsALeaseOnTheSnapshotItServesAndReleasesTheOneItLeaves` and `aLeaseHoldsItsSnapshotUntilItIsReleased` (the sibling test in `MarketplaceCacheTests` that showed the same true cause) both passed every time. This is three times past the ten-run bar this task set.

## What

`theStoreHoldsALeaseOnTheSnapshotItServesAndReleasesTheOneItLeaves` in `Tests/FoundationModelsSkillsTests/MarketplaceStoreTests.swift` fails in about one of four full `swift test` runs. It passes every time when it runs alone, and it passes with `--filter MarketplaceStoreTests`.

The behavior is present before the update-check work of ^6drye1r: a run of the suite with that work stashed showed the same failure rate. Thus it is a test problem, not a store problem.

Probable cause: `MarketplaceStore.serve(atIndex:sha:displayID:catalogVersion:)` takes the lease with `try? entry.cache.leaseCurrentSnapshot()`. Under a full parallel run the process holds many open files, thus the `open(2)` of the lease can fail and the lease becomes `nil` with no finding. The test then sees the new snapshot folder as not locked.
