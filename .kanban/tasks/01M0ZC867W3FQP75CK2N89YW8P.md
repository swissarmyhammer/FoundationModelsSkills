    Reproduction before the fix: 12 bounded runs of `swift test`. Run 2 hung (killed at 90 s). Run 4 failed (rc=1, 55 s). The other 10 runs were green in 10 to 13 s.

    Evidence from the hung helper (pid 37911):
    - `sample` showed only 2 threads: the main thread in `CFRunLoopRun` (idle) and one idle worker thread. No thread was blocked in a lock or a syscall.
    - `lsof` showed 4 open `O_EVTONLY` descriptors on the temp root of `hotReloadEndToEndFiveStepScenario` (`alpha`, `bravo`, `charlie`, root). The watcher was live and correct. No child process, no open pipe.
    - The test log showed that `hotReloadEndToEndFiveStepScenario` started and never reported a result. All other tests reported a result. The disk state of the temp root (bravo v1, charlie v1) showed the test stopped in step 1.
    - In the same run, `selectionTierSearchesThroughAScriptedAgentSessionAfterReload` failed with `afterFirst == 0`: the reload publication did not reach its subscriber in 10 s.
    - In run 4, all 9 `SkillsRegistryReloadTests` that subscribe to `onReload` or `commandUpdates` failed with the same `afterFirst == 0`. `SkillWatcherTests` (the watcher alone) passed.

    Two causes:
    1. The hang. `HotReloadTests.waitUntilBlockedOrTimeout` raced `EmbedGate.waitUntilBlocked()` (a `withCheckedContinuation` that only `waitUntilOpen()` resumes) against a `Task.sleep` in a `withTaskGroup`. When the timeout won, `cancelAll()` did not resume the continuation, and `withTaskGroup` waits for all children before it returns. The test suspended forever, so the helper process never exited.
    2. The trigger. Every reload subscription in `HotReloadTests` and `SkillsRegistryReloadTests` called `registry.onReload` (or `commandUpdates`) inside a `Task { }`. The subscription registers only when the task first runs. Under a loaded cooperative pool (all 377 tests start together) the task can start after the watcher's first publication (200 ms debounce). `ReloadBroadcaster` sends a publication only to subscribers that exist at that time, so the first publication was lost and the test waited 10 s for nothing.

    Fix (tests only, no library change):
    - `HotReloadTests`: `subscribe` reads `registry.onReload` before it creates the task. `waitUntilBlockedOrTimeout` polls `EmbedGate.isBlocked` with `ReloadTestSupport.poll`; `waitUntilBlocked` and `blockedWaiters` are removed.
    - `ReloadTestSupport.tally(_:into:)`: new helper that takes an already-subscribed stream and counts its elements in a task.
    - `SkillsRegistryReloadTests`: `subscribe` reads `registry.onReload` before the task; the 4 inline `Task { guard let stream = registry.commandUpdates ... }` subscriptions use `ReloadTestSupport.tally`.

    Reproduction after the fix: 10 bounded runs, all green, 10 to 12 s each.

## What
During the finish batch on 2026-08-26, a full `swift test` run stopped four times after every test had passed. The `swiftpm-testing-helper` process (test bundle `FoundationModelsSkillsTests.xctest`, `--testing-library swift-testing`) stayed alive and did not exit. A normal run finishes in 9-15 s. The hang occurred at random, not on one test. `kill` of the helper and one new run gave a green result each time. Seen on tasks ^qxytjzw, ^bb54djj, ^tb86z9q, ^2dzxvms.

Probable cause: a test leaves a live resource that keeps the process alive after the last test — for example a `SkillWatcher` dispatch source, a `DispatchSourceFileSystemObject` on a temp directory, a `Process` child, or a task that waits on an `AsyncStream` (`onReload`) with no cancellation.
